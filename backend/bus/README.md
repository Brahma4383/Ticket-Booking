# Bus API

The booking backend for the bus flow in `frontend/src/pages/bus`. Every
travel mode has one; this is the bus module.

Everything it returns matches `frontend/src/types/bus.types.ts` exactly —
camelCase keys, string ids, the same three seat statuses.
`frontend/src/services/bus.services.ts` calls it directly.

## Running it

MySQL has to be up with `schema.sql` already applied.

```bash
cd backend
myvenv/Scripts/python -m pip install -r requirements.txt

cp .env.example .env          # then set DB_PASSWORD in it

myvenv/Scripts/python manage.py migrate       # Django's own admin/auth tables
myvenv/Scripts/python manage.py runserver
```

`settings.py` reads `backend/.env` at startup; a variable already set in the
real environment wins over the file. `.env` is gitignored - the password
belongs there, not in `.env.example`.

`migrate` creates nothing for the bus tables. Every model in this app is
`managed = False` and maps onto a table `schema.sql` already made, so the
CHECK constraints and composite unique keys stay exactly as written rather
than being regenerated by the migration autodetector. **A schema change goes
into `schema.sql`, gets applied to MySQL, and is then mirrored in
`models.py`** — not the other way round.

## Endpoints

All under `/api/bus/`.

| | | Backs |
|---|---|---|
| `GET` | `trips/?from=&to=&date=` | `searchBuses(query)` |
| `GET` | `trips/<id>/?date=` | — (reload / deep link) |
| `GET` | `trips/<id>/seats/?date=` | `fetchSeatLayout(trip)` |
| `POST` | `quote/` | `calculateFare(seats)` |
| `POST` | `bookings/` | `confirmBooking(input)` |
| `GET` | `bookings/<pnr>/` | — (ticket lookup) |

### `GET trips/`

`from` and `to` are city names as typed into the search box, matched
case-insensitively against `city.name`. Returns `BusTrip[]` sorted by
departure.

`fareFrom` and `seatsLeft` are **for that date**: the cheapest seat still
buyable and how many are left, not the trip's list price and capacity.
Filtering and sorting stay on the client — `pages/bus/filters.ts` already does
both, and one route's services for one day is a short list.

### `GET trips/<id>/seats/`

Returns `Deck[]`, lower deck first. `rows` and `columns` are the grid extent
and `aisles` are the columns inside it holding no seats, so a coach with an
unusual arrangement still draws correctly.

The date matters. `status` is per date — a seat sold for Tuesday is still on
sale for Wednesday. The three statuses the map knows are:

- `available`
- `ladies` — bookable, but only for a female passenger
- `booked` — either sold for this date, or `blocked` in the database

### `POST quote/`

```json
{ "tripId": 12, "date": "2026-09-25", "seatIds": ["L4", "L5"] }
```

Returns a `FareBreakdown` plus `unavailableSeatIds`. The front end computes the
same figures locally so the summary updates as seats are ticked; this is the
authoritative version. Calling it before payment catches seats that went while
the traveller was filling in the form.

Pricing is ₹25 service fee and 5% GST rounded to whole rupees — the same three
constants as `bus.services.ts`, deliberately duplicated so the summary needs no
round trip.

### `POST bookings/`

```json
{
  "tripId": 12,
  "date": "2026-09-25",
  "seatIds": ["L4", "L5"],
  "passengers": [
    { "seatId": "L4", "name": "A Rider", "age": "29", "gender": "male" },
    { "seatId": "L5", "name": "B Rider", "age": "31", "gender": "female" }
  ],
  "contact": { "email": "rider@example.com", "phone": "9876543210" },
  "boardingPointId": 45,
  "droppingPointId": 78,
  "paymentMethod": "HDFC Bank",
  "paymentMethodId": "netbanking",
  "userId": null
}
```

Returns `201` with a `BookingConfirmation` — the whole ticket, trip and seats
embedded, nothing left to fetch. It also carries `status`, which
`bus.types.ts` does not have yet.

Differences from `ConfirmBookingInput`, which the front end will need to map:

- `trip`, `seats`, `boardingPoint` and `droppingPoint` go out as **ids**, not
  objects. The server re-reads them; a client cannot be trusted on price.
- `query` is not sent. The trip already knows its cities, and the response
  echoes a `query` back.
- `paymentMethodId` says which of the four methods the label belongs to.
  `payment.method` only admits `upi`, `card`, `netbanking` or `wallet`, and the
  label goes in `payment.instrument`. `PaymentStep` passes both.
- `userId` is optional. Leaving it out is a guest checkout, which the schema
  allows (`booking.user_id` is nullable).

Seats are held with `SELECT ... FOR UPDATE` for the length of the
transaction, so two people checking out the same seat are serialised rather
than both passing the availability check. `uq_bus_seat_per_date` stands behind
that. A booking that fails anywhere rolls back whole — no half-sold seat.

### `GET bookings/<pnr>/`

Same `BookingConfirmation`. The reference is case-insensitive. A ticket still
reads back after its service is withdrawn from sale.

## Errors

One envelope, whatever failed:

```json
{ "error": { "code": "seat_unavailable", "message": "...", "detail": { "seatIds": ["L4"] } } }
```

| Code | Status | |
|---|---|---|
| `invalid` | 400 | Field validation; `detail` is the per-field errors |
| `invalid_seat_selection` | 400 | Seat not on this bus, ladies seat with a male passenger, stop point off-route, date past |
| `seat_unavailable` | 409 | Taken while the traveller was deciding, or withdrawn from sale |
| `trip_not_found` | 404 | |
| `booking_not_found` | 404 | |

409 rather than 400 on a lost seat: the request was well formed, the inventory
moved underneath it. That is the one the results page should re-query on.

## Layout

| | |
|---|---|
| `models.py` | Tables, all `managed = False` |
| `serializers.py` | DRF serializers validate input; `serialise_*` functions shape output |
| `services.py` | Every business rule — search, pricing, the booking transaction |
| `views.py` | Validate, call one service function, render. Nothing else |
| `exceptions.py` | The error types and the handler that gives them one shape |

## This app owns its models

`city`, `app_user`, `offer`, `booking`, `booking_fare_line` and `payment` are
not bus tables — every mode uses them — but each module maps them under its own
model classes rather than sharing an app. No module imports another, so any one
of them can be changed or dropped on its own.

That works because they are all unmanaged: Django's `models.E028`
duplicate-table check only collects managed models, nothing tries to create a
table twice, and each app's foreign keys stay inside its own app so no reverse
accessor collides. **Keep every model in this app unmanaged.**

## Not done

**There is no cancellation endpoint.** `uq_bus_seat_per_date` admits one
`bus_booking_seat` row per seat per date regardless of booking status, so the
row *is* the reservation and releasing a seat means deleting it — which loses
the passenger manifest for a cancelled ticket. That needs a decision about the
schema (a status column on the seat row, or a partial index) before code.
Availability is read the same way throughout: a row means sold, full stop.

## Tests

```bash
myvenv/Scripts/python manage.py test bus
```

33 tests covering search and date-aware availability, the deck grid, the fare
formula, the booking transaction, double-booking, ladies seats and lookup.

They run against SQLite, building the unmanaged tables with the schema editor,
so they need no MySQL server — the point is to pin behaviour, not storage.
What they therefore do **not** exercise is the MySQL side: the CHECK
constraints and `uq_bus_seat_per_date` exist only in `schema.sql`, so the
double-booking test proves the service layer's own check, not the constraint
standing behind it.
